# Interface decisions

One top bar holds the collection and review selectors, so navigation stays out of the diff’s way. In the review selector, a review linked to a pull request shows the PR’s state under its progress, plus its checks and any approval or requested changes while it’s open; opening the selector re-reads them. The PR’s link stays in the review header, because a link inside a list option can’t be reached by keyboard. Collections express a curated reading order; the separate Git ancestry tab reports actual dependencies. Each review and change group leads with a human name and an explanation in Markdown; a review description past three lines folds behind Show more, and a review’s card on its collection shows the words without the Markdown. Descriptions were plain text first, so a line break stays a line break. Text that looks like HTML shows as typed wherever Preread renders Markdown, because authors write placeholders such as `user:<id>` and none should vanish. The branch and a plain-language summary of the comparison share the tab row, and the folder, mode, and base open from that summary. Beside them, the line count covers runtime code only, so tests, evals, and lockfiles don’t inflate it; hovering or clicking it shows each kind and the total. A commit SHA base stays out of the summary because it tells the reader nothing. Diff layout, whitespace, wrapping, and theme sit behind one settings button.

The file outline is an index into a continuous review, not a single-file filter. Within each group, files sit under a row for their folder; a long folder drops its leading folders rather than cutting through a name. Each file takes one line: an icon for its kind (code, test, styles, docs, config, data, SQL, script, lockfile, image, and a few more), its name, and a meter of its changed lines, green for added and red for removed, on a log scale so a one-line fix and a 500-line rewrite both read at a glance. Modified files carry no letter; new, deleted, renamed, and untracked files keep theirs, because the meter can't tell a new file from one that only gained lines. Hovering a file shows its full path, status, kind, and exact line counts, and hovering a shortened folder shows all of it. Dragging the outline's edge, or pressing arrow keys on it, widens it for long folders, up to half the window; the browser keeps that width, and a double-click or Enter restores the default. Kinds differ by shape, not color, because color already means added, deleted, or renamed. A renamed file's card title reads old path → new path, with the changed folders and name parts marked like changed words in a diff, and outline search matches old paths too. A file whose diff has no lines to show, such as a pure rename, says what changed instead of drawing an empty diff. Every changed block appears in its assigned group or Other changes. Whole-file and partial-file groups share the same review controls; partial selections include complete hunks with context and are labeled Selected blocks. A changed image shows each version that exists, stacked in unified view and side by side in split view, over a checkerboard that shows only through transparency.

⌘-click (Ctrl-click off a Mac) on a name, in the diff or in the source viewer, opens where it’s defined in a full-window viewer of the worktree as the review shows it: a call, a constant, a type, a component, a prop or a property. Holding the key underlines what can be followed, the way an editor does, so plain reading never shows link styling. A name with no definition, or one defined on the line clicked, says so beside it instead of opening anything. Words in strings, comments and JSX text stay plain, even where the syntax colors give out partway through a TSX file. A prop, an object’s key or a destructured name opens the property its type declares, and a shorthand `{ limit }` opens the value it copies. Only calls take Tab, because a drag that starts on a focusable name selects no text. A library call opens the installed package’s source with its name and version beside the path, and a method follows its value’s type, so `query.where` lands on the query builder’s `where`. Each file card’s expand button opens its file in the same viewer, at the card’s first change. A changed file shows as one whole-file diff in the review’s layout, wrapping and whitespace setting, so a definition reads alongside what changed around it; an unchanged file, or one whose only changes are hidden whitespace, shows plain source. A call on a removed line follows into the base version, so a deleted file’s definition still opens, every line removed. The Explorer beside the code is the whole worktree, not the change list: a folder takes the color of what changed inside it and counts those files, open folders pin under their parents so a 500-file folder never hides where the reader is, collapsing a pinned folder keeps it in view, and the open file’s folders stay marked while collapsed. A changed file opened from the Explorer starts at its first change. Each part of the path above the code reveals that folder in the tree. Back and Forward (⌘[ and ⌘]) return to each place at its scroll position. Open in editor appears only while the file on disk matches what the viewer shows; otherwise the viewer says it’s showing the reviewed version.

A group receipt records the diff content and description the user reviewed. Once a group’s header scrolls away, a slim bar fades in at the top with the group’s number, name and Mark all viewed, and each file’s name sticks beneath it; the bar leaves with the group’s last file. Marking from that bar folds the group and moves on to the next one, the way Viewed moves on to the next file. Missing selections and overlapping groups are explicit states. While groups are left, the review title carries Mark review viewed and the collection page carries Mark collection viewed; each marks the remaining groups as their own buttons would, skips groups that need attention, and leaves a review untouched, saying why, if its content changed after the page loaded. Reviewed does not imply approval to push or publish. Group status, Viewed marks and comments on code live on disk; notes from before comments stay in the browser until the reader sends or deletes them. A comment whose file has left its review, as when an agent moves a change to another part of a stack, gathers above the diff. Its file name opens the file in the source viewer at the comment’s line, and a link on the same line jumps to each other part that shows the file now, with Back returning to the comment.

An overview reads like a book about the change. The Contents rail on its left lists the feature overview and every part, numbered, with each part’s review status, so a fifteen-part feature still fits one glance; the open overview’s headings sit under it and follow the reader’s scrolling. Counts and question marks there say where comments and open questions are without opening anything. Each section ends with the code groups it explains. Their Mark reviewed button does exactly what Mark all viewed does in the diff, so approving code from an overview and from the diff can’t disagree, while approving a code excerpt stays separate from marking its group. A part ends with its full group checklist and links to the parts before and after it, and every linked group’s header in the diff links back to its place in the overview. Below 1180 px the rail becomes a drawer, so the document keeps its reading width.

Feedback is a conversation. Every answer, approval and comment is a thread whose state follows from who spoke last, so a status can’t disagree with what was said. Either side resolves; a reply, Reopen or an edit hands it back to the agent. What waits on the reader leads each list in the accent color, and resolved items fold away rather than disappear. Each reply is its own file, so an agent writing from a terminal and a reader writing in a tab can’t overwrite each other. Comments and replies read as Markdown so code reads as code: a fenced block takes syntax colors, and one that names no language in a comment on code takes its file’s, since a reviewer quoting a fix rarely labels it. Comments were plain text first, so a line break stays a line break and text that looks like HTML stays as typed instead of vanishing; previews show the words without the Markdown.

Light and dark palettes use semantic tokens for canvas, surfaces, text, borders, syntax, additions, deletions, warnings, and focus. System is the initial preference. Syntax-highlight spans have transparent backgrounds so they cannot erase a diff’s meaning. The change meter’s green and red also differ in lightness, so color-blind readers can still tell them apart. Status text and icons supplement color.

The mark is a pair of reading glasses whose lenses are a diff’s minus and plus, drawn in the canvas color on an accent tile. The wordmark mutes “pre” so “read” leads.

Native buttons, dialogs, and form controls provide keyboard behavior; the custom pickers implement listbox keyboard navigation. Focus remains visible. Reduced-motion disables animation. Narrow screens keep collection navigation and continuous diffs while hiding the optional file outline. Errors, loading, empty comparisons, missing files, and unavailable previews are explicit. A refresh, from the toolbar or from an agent, re-reads behind the current view and keeps the reader’s place; only a server restart or an explicit page reload replaces the page.
